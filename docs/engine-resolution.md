# 效果暂停与恢复

`server/game/resolution.go` 管理顺序效果的等待关系。它不改变伤害批次、死亡检查或同批触发的规则，也不是完整的可序列化任务系统。卡牌仍用显式 Go 行为实现。

## 顺序效果

当后一步必须等前一步产生的选择、防御或反制完成后才能执行时，使用：

```go
e.runResolution("effect name",
    func() { /* 打开选择或发起法术 */ },
    func() { /* 前面的交互全部结束后执行 */ },
)
```

每一步只启动一次。结算帧记录步骤索引，以及正在等待的 `PendingAction` 或 `SpellCast`。选择对象和法术对象分别持有等待它们的帧；业务 callback 不再被包装。帧保留创建时的法术作为 baseline：命中前选择的后续步骤可以继续原法术，而回合末父流程必须等待新产生的法术。

`Combine` 仍是同步 handler 组合器。不要用它表达“等待玩家选择，然后继续”；不要把同批群体伤害的每个目标自动拆成等待步骤。

## 现有调用点的迁移

已有代码在打开选择后调用 `continueAfterPendingAction(fn)`，将恢复步骤挂到当前选择。只有没有当前选择时该 helper 才不做任何事。需要给排队但尚未展示的选择挂恢复步骤，使用 `addActionContinuation(action, name, fn)`。

选择成功后先推进已有选择队列，再恢复父流程。失效的排队选择跳过业务 callback，但其父流程仍需等待剩余有效选择。选择 callback 返回错误时，窗口和等待帧保留供重试；这不是状态回滚，callback 仍必须在修改状态前完成可能失败的校验。

通过 `completePendingSpell` 结束法术。反射法术使用 `replacePendingSpell` 转移父流程；不要在卡牌代码中直接搬运等待帧。替换函数发生错误前必须完成校验且不修改游戏状态。所有结算步骤在游戏结束后停止恢复。

## 维护与验证

回合末流程是迁移示例：收集回合末触发、处理对方回合末临时效果、执行清理。第一步仍收集完整触发批次，后续步骤等待选择和法术。

修改此协议时检查 `resolution_test.go` 的选择重试、嵌套选择与法术、baseline、失效队列、法术反射和游戏结束测试，以及 `reported_bugs_test.go` 中 #158/#160 的真实卡牌场景。执行完整 Go 测试、vet、race 检查和两客户端浏览器流程。规则事件、修正生命周期、状态操作和影响检查的整体边界见 [引擎架构](engine-architecture.md)。

# 规则执行报错后的权威同步

这次修复关闭了质量复核中“部分修改后报错但 revision 不变、客户端不同步”的缺口。不实现通用事务回滚，不改变血沙等现有规则的付款/报错含义。

## 明确边界

`HandleActionWithRevision` 持有原引擎锁，先检查 expected_revision、玩家/引擎有效性和动作名。执行前拒绝不进入结算、不推进版本。通过这些检查后，已知动作进入原有规则处理器与原有 deferred resolution；无论返回成功还是 error，都在这些 defer 完成后推进一次 revision，再记录这个请求对应的 revision，最后解锁。阶段不允许、目标不合法等处理器内拒绝即使没有修改游戏状态，也保守地推进版本。

WebSocket 在函数返回（引擎已经解锁）后发送原始错误/成功回执，并调用现有 `room.BroadcastState()`。即使是 stale 预校验拒绝，也发送当前权限过滤快照，让过期客户端追上状态。JSON 解码失败、client_log、观众尝试行动和未开始的游戏仍在外层拒绝，不进入规则。

没有从引擎事件回调中同步读取状态，也没有在持有引擎锁时重新调用 GetStateForPlayer；广播沿用房间锁下收集接收者、释放房间锁后读取引擎视图的路径。双方和观众收到的均是既有权限过滤视图，不传内部结算帧或私有候选。

## 前端语义

回执新增 `revision` 和 `state_advanced`。后者表示请求进入过规则执行，并不表示一定修改了游戏事实。

- 执行报错：显示原始错误，但继续锁住旧草稿，直到更高版本快照到达；新快照清掉旧付款/选择/草稿，并保留与这个版本对应的错误。用户必须基于新事实重新选择。
- 执行前拒绝：没有新版本时保留本地草稿与错误；若收到更新的服务器版本，仍清掉陈旧草稿。
- 状态先于回执：只允许相同请求、相同已同步 revision 的迟到错误更新错误提示；不会清除新决策或解锁新请求。跨越更多版本或已提交新请求的旧回执不影响当前交互。错误原文也保留在本地操作记录。
- 同一个失败 pending 窗口可以保留 decision_id，但 revision 必须变化；重用旧 expected_revision 的请求先于回调被拒绝。完成后激活下一窗口仍分配新的 decision_id。
- 断线不自动重发；广播与回执不是网络上的原子交付，断线仍需要重新同步。

## 实证

真实卡牌“蔽天阵 血沙”：2 生命单位请求支付 2 点生命，原回调先扣到 1，再返回 `cannot pay life from selected unit`。新增 Go 测试保留该实际部分修改与原始错误，断言 revision 前进、pending ID 保留、旧请求不可再次进入回调、无修改拒绝也版本化及权限过滤。

新增 `tests/frontend_failed_action.py` 用两个实际 Vue 玩家和一个观战客户端运行上述流程。三方收到同一新版本，双方战场看到生命降为 1；拥有者旧草稿/选项清空且原始错误仍可见；对手和观众没有私有候选或手牌。随后验证无修改错误、未知动作的执行前拒绝保留草稿、重新选择后成功交接到新 pending 并恢复主回合。

Node 测试覆盖错误回执先于/后于快照、等待同步期间禁重试、旧草稿、连续决策、旧回执不能解锁新动作。既有拒绝召唤测试现在单独断言 revision +1，并继续逐字段比较其余完整玩家视图不变；没有放宽费用/吞噬不能被错误扣除的规则断言。

## 不保证

不回滚失败回调已做的部分付款或其他修改；不重写既有回调构造候选的规则。保守版本推进会使未改动游戏事实的规则拒绝也使双方本地草稿失效。旧客户端仍可省略 expected_revision；没有持久请求去重、跨进程 epoch 或跨重启幂等保证。本修复覆盖正常返回 error 的执行路径，不提供进程崩溃后的交付保证。

# 重建与开发准则

本文档记录《奥术纪元 / Era of Arcane》重建阶段的非规则类要求。它用于替代旧根目录文档中分散、混乱、容易过期的工程说明。

本文档不定义具体游戏规则，不定义单张卡牌效果，也不作为卡牌文本来源。规则请写入 `docs/rules/`，当前运行方式请参考 `docs/project/current-runtime.md`。

## 1. 当前重建目标

当前目标是先把游戏框架整理成可维护、可测试、可扩展的形态，再重新导入和实现卡牌。

优先级顺序：

1. 定稿核心规则
2. 统一术语和卡牌文本表述规范
3. 梳理游戏框架和运行流程
4. 设计稳定的后端动作、支付、窗口、可见性模型
5. 让前端严格跟随后端状态展示可执行动作
6. 重新整理卡牌文本和卡牌数据
7. 分批实现卡牌效果并补测试

在规则和框架未稳定前，不以某一张旧卡牌的旧实现作为架构设计依据。

## 2. 规则文档协作流程

推荐采用反复迭代的方式整理规则：

1. 规则作者先手写一版认为严谨的规则说明
2. 开发者阅读后，把内容整理进 `docs/rules/` 的正式 Markdown 文档
3. 开发者反馈歧义、冲突、实现风险和需要补充的边界条件
4. 规则作者根据反馈补充细则
5. 重复以上过程，直到规则足够稳定
6. 规则稳定后，再进入代码和卡牌实现

整理规则时要重点检查：

- 玩家是否能读懂
- 程序是否能判断
- 前端是否能展示
- 测试是否能覆盖
- 是否存在隐藏信息泄露风险
- 是否与已定术语冲突

## 3. 文档分工

建议文档按职责拆分，避免一个文件承担所有内容。

规则类：

- `docs/rules/core-rules.md`：核心规则
- `docs/rules/glossary.md`：术语表
- `docs/rules/card-text-style-guide.md`：卡牌文本表述规范

项目类：

- `docs/project/current-runtime.md`：当前游戏实际运行方式
- `docs/project/development-guidelines.md`：重建与开发准则

后续可以新增：

- `docs/project/architecture-plan.md`：新框架设计
- `docs/project/action-window-model.md`：动作窗口模型
- `docs/project/payment-model.md`：支付模型
- `docs/project/visibility-model.md`：信息可见性模型
- `docs/project/testing-plan.md`：测试路线图
- `docs/cards/`：重新整理后的卡牌文本和审计结果

旧的根目录进度文档只能作为历史参考。若内容与 `docs/` 下的新文档冲突，以新文档为准。

## 4. 技术栈约束

当前后端：

- Go
- 标准 `net/http`
- `github.com/gorilla/websocket`
- 内存房间和内存对局状态
- 暂无数据库

当前前端：

- 静态 HTML、CSS、JavaScript
- Vue 3 通过 CDN 加载
- 暂无 npm 前端构建步骤
- 卡图从远程静态资源加载

当前服务方式：

- 一个 Go 进程同时提供 API、WebSocket 和静态前端文件
- 前端 API 应使用相对路径
- WebSocket 应基于 `location.host` 建立连接
- 不要把浏览器端请求硬编码到 `localhost`

除非后续明确决定重构技术栈，否则不要在重建规则和框架期间引入大型前端构建系统、数据库或多服务部署架构。

## 5. 运行方式

当前服务需要从 `server` 目录启动：

```powershell
cd server
go run .
```

启动后访问：

```text
http://localhost:9090/
```

常用页面：

- `/`：大厅
- `/game.html`：对局界面
- `/card-test.html`：测试工作台

## 6. 工程原则

核心原则：让游戏能从结构化代码和正式规则文档中被理解，而不是从旧描述文本中被猜出来。

开发时应遵守：

- 优先阅读现有代码、测试和 `docs/` 下的新文档
- 保持改动范围清晰，不把无关重构混入规则或功能改动
- 通用规则写进规则层或引擎层，不写进前端猜测逻辑
- 前端展示后端给出的合法动作，不自行推断复杂规则
- 隐藏信息由后端控制，不为了调试向前端泄露非法信息
- 运行时行为应使用结构化字段、接口、状态或行为对象表达
- 不通过解析卡牌描述文本推断机制
- 不新增依赖旧卡牌中文描述的 `contains`、`includes` 等判断
- 新增共享机制时应同时考虑测试和前端展示

## 7. 卡牌重建边界

当前阶段先不重写单张卡牌效果。

在卡牌文本和规则重新整理前，不建议：

- 批量修改旧卡牌行为
- 为某张旧卡临时增加特殊解析逻辑
- 把扩展包卡牌加入运行时卡池
- 让旧卡牌实现反向决定新规则
- 把旧 JSON 快照当成正式规则来源

后续重新导入卡牌时，应先完成：

1. 卡牌文本规范
2. 术语表
3. 卡牌数据字段设计
4. 卡牌审计流程
5. 卡牌实现和测试分批计划

## 8. 测试要求

后端改动后默认运行：

```powershell
cd server
go test ./...
```

以下改动不能只依赖 Go 单测，还需要浏览器级检查：

- `web/game.html`
- `web/css/game.css`
- WebSocket 状态结构
- 行动窗口
- 目标选择
- 支付流程
- 防御或反应流程
- 回合流程
- 游戏结束流程

建议前端最小检查流程：

1. 启动服务
2. 创建房间
3. 使用两个真实前端客户端加入
4. 双方完成起手流程
5. 学习技能
6. 获取或支付资源
7. 使用一次主动效果或法术
8. 处理一次防御或反应窗口
9. 处理一次弃牌等待动作
10. 确认双方都能看到游戏结束或稳定状态

如果某次改动无法完整跑测试，应在提交或交付说明中明确说明原因。

## 9. 前端设计方向

当前视觉方向应保持为中文奇幻桌游工具界面。

整体风格：

- 深色黑棕桌面质感
- 细金色边框
- 方正控件，避免胶囊按钮
- 中文奇幻感衬线字体
- 大厅和测试台偏克制、工具化
- 对局界面信息密度高但保持可读

避免引入：

- 通用 SaaS 风格
- 大面积亮蓝面板
- 紫色渐变主视觉
- 大圆角卡片堆叠
- 营销式 landing page 结构

前端功能设计原则：

- 玩家当前能做什么必须清楚
- 玩家不能做某动作时应能看到原因
- 支付、目标、防御、反应等复杂流程要有明确窗口状态
- 绑定、衍生、临时效果要能在详情面板中被理解
- 不要为了美观牺牲隐藏信息边界

## 10. 部署方向

当前最简单的部署方式是一个 Go 服务放在反向代理后面：

```text
Nginx/Caddy HTTPS
  -> http://127.0.0.1:9090
      Go server
        /api/*
        /ws
        static web/*
```

当前不适合多实例部署，因为房间和对局状态都在单进程内存中。

## 11. 已知工程限制

当前限制：

- 房间和对局状态在内存中
- 服务重启会丢失所有房间
- 暂无认证
- 暂无限流
- 暂无数据库
- 暂不适合多实例部署
- 旧根目录文档可能过期或互相冲突

重建时应优先相信：

1. 新 `docs/` 文档
2. 当前代码
3. 当前测试
4. 最近 Git 历史
5. 旧根目录文档中的历史信息

## 12. Git 要求

开发时应保持 Git 历史可读。

要求：

- 开始较大改动前先查看工作区状态
- 不覆盖用户未提交改动
- 不提交生成二进制文件
- 不提交过期进度笔记
- 提交应小而清晰
- 规则文档、框架代码、卡牌数据尽量分开提交
- 如果修改生成文件，应能说明生成来源和命令

长期问题跟踪建议使用 GitHub Issues。若没有正式版本号，Issue 中应记录测试用的提交哈希。

## 13. 旧文档迁移策略

旧根目录文档中的内容不要一次性照搬进新体系。

迁移原则：

- 当前仍准确的工程事实，整理进 `docs/project/`
- 正式规则，整理进 `docs/rules/`
- 单张卡牌问题，等卡牌重建阶段再进入 `docs/cards/` 或 Issue
- 过期进度、旧猜测、已被推翻的实现方案，不再迁移
- 迁移后的内容应能独立阅读，不依赖旧文档上下文

当新文档覆盖旧文档职责后，可以逐步删除或归档旧根目录文档。

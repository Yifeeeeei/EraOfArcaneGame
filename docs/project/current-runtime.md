# 当前游戏运行方式说明

本文档用中文描述当前仓库中游戏原型的运行方式，供后续重建框架时参考。它类似项目地图，不是正式规则文档，也不是卡牌效果清单。重建时应优先关注整体架构、数据流和运行边界，暂时不要围绕某一张卡牌的旧实现做设计。

重建和开发过程中的非规则类要求，请参考 docs/project/development-guidelines.md。

## 1. 项目定位

当前项目是《奥术纪元 / Era of Arcane》的浏览器双人对战原型。

当前目标不是完整发行版，而是让基础包能在真实前端中进行双人测试，并逐步把规则、框架和卡牌效果整理到可维护状态。

## 2. 当前技术结构

后端使用 Go 编写，前端使用静态 HTML、CSS、JavaScript，并通过 CDN 加载 Vue 3。

当前没有数据库。房间、玩家和对局状态都保存在 Go 服务进程内存中。服务重启后，房间和对局会丢失。

同一个 Go 服务负责：

- 提供 HTTP API
- 提供 WebSocket 对战连接
- 提供前端静态文件
- 加载编译进 Go 代码中的基础卡牌数据
- 注册并执行卡牌行为

## 3. 启动方式

当前服务需要从 `server` 目录启动，因为部分路径仍使用相对路径。

```powershell
cd server
go run .
```

启动后访问：

```text
http://localhost:9090/
```

主要页面：

- `/`：大厅页面
- `/game.html`：正式对局页面
- `/card-test.html`：卡牌测试工作台

主要接口：

- `/api/cards`
- `/api/deck/validate`
- `/api/room/create`
- `/api/room/list`
- `/api/room/info`
- `/ws`

## 4. 卡牌数据来源

当前运行时不从 JSON 读取卡牌池。

基础包卡牌数据已经编译在 Go 文件中，主要来源是：

```text
server/cards/definitions_gen.go
```

参考快照位于：

```text
data/supported_card_infos.json
```

重建期间，这份 JSON 可用于审计和对照，但不应被当成运行时规则来源。

## 5. 卡牌行为来源

当前项目中，卡牌效果主要通过 Go 代码显式实现。

常见位置：

```text
server/game/card_<卡号>_<名称>.go
server/game/card_behavior.go
server/game/card_effects_catalog.go
```

重要原则：

- 不应通过解析卡牌描述文本来推断效果
- 不应新增根据中文描述 `contains` 或类似方式判断机制的代码
- 新机制应通过明确接口、结构体、状态字段或行为对象实现
- 单张卡牌的旧行为可以作为参考，但重建规则时不要被旧实现绑定

## 6. 当前后端运行流程

整体流程大致如下：

1. `server/main.go` 启动服务
2. 加载编译后的基础卡牌定义
3. 设置可游玩卡牌数据库
4. 注册卡牌行为工厂
5. 注册 HTTP API、WebSocket 和静态文件服务
6. 玩家通过前端创建或加入房间
7. 房间满员后创建内存对局状态
8. 前端通过 WebSocket 发送动作
9. 后端引擎校验动作、修改状态并广播新状态

## 7. 当前前端运行流程

前端主要由以下文件组成：

```text
web/index.html
web/game.html
web/card-test.html
web/css/main.css
web/css/lobby.css
web/css/game.css
```

当前前端不需要 npm 构建步骤。

前端职责：

- 展示大厅和房间
- 连接 WebSocket
- 展示双方场面、手牌、技能、物品、墓地等信息
- 根据后端状态展示可用动作
- 发起学习、召唤、消耗、施放、防御、弃牌等操作
- 在部分复杂支付或选择窗口中收集玩家选择

## 8. 房间与对局状态

房间和对局目前是内存对象。

本地调试日志会写入：

```text
server/logs/rooms/*.jsonl
```

这些日志通常不进入 Git。复现前端对局问题时，应优先查看对应房间日志。

## 9. 当前架构边界

当前项目已经具备可玩的雏形，但还有一些需要重建时特别注意的边界。

### 规则边界

目前部分规则分散在引擎、辅助函数、卡牌行为和前端判断中。重建时应把通用规则沉淀到核心规则层，再让卡牌调用规则能力。

### 卡牌边界

当前基础包卡牌已经有大量 Go 行为文件。后续你计划重新更新卡牌，并可能从另一个仓库拉取卡牌资料。因此当前阶段不要围绕单张卡牌逐一修效果，而应先确保框架能表达正式规则。

### 前端边界

前端应展示后端允许的动作，而不是自行猜规则。对于支付、目标、反应、防御等复杂流程，前端需要清楚展示当前窗口和可选项。

### 信息边界

隐藏信息必须由后端状态控制。前端不应收到对手手牌、牌库顺序、隐藏实例 ID 等不该知道的信息。

## 10. 重建阶段建议

建议按以下顺序推进：

1. 定稿核心规则文档
2. 定稿术语表
3. 定稿卡牌文本表述规范
4. 梳理当前引擎中的通用规则能力
5. 设计新的动作窗口和支付窗口模型
6. 让前端动作完全跟随后端状态
7. 再开始导入或重写卡牌文本
8. 最后逐批实现具体卡牌效果并补测试

## 11. 当前阶段不要做的事

在规则和框架未整理前，暂时不要：

- 逐张修旧卡牌效果
- 因某张卡临时增加描述文本解析
- 把扩展包卡牌加入运行时卡池
- 把隐藏信息暴露给前端方便调试
- 大规模改视觉风格
- 把前端迁移到 npm 构建体系，除非后续明确决定

## 12. 最低验证方式

后端改动后至少运行：

```powershell
cd server
go test ./...
```

涉及前端、WebSocket 状态、行动窗口、目标选择、支付流程或回合流程时，还需要进行真实浏览器检查。

建议浏览器检查流程：

1. 启动服务
2. 打开卡牌测试工作台
3. 创建房间
4. 用两个前端客户端加入
5. 双方完成调度
6. 学习技能
7. 消耗获得元素
8. 施放法术
9. 处理防御或反应窗口
10. 处理弃牌等待动作
11. 确认双方都能看到游戏结束
